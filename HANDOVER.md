## 6. Feature A — playable Piano Roll via a connected keyboard (Web MIDI) — 2026-10-21

A connected MIDI keyboard now plays the Piano Roll's selected channel through the existing audio engine, highlights held keys on the roll, and can record the performance into the active pattern. Everything is zero-dependency and static-hosting-safe.

### What shipped

- **`app/public/midi-input.js` (new).** Two layers, both DOM-free:
  - `MidiStreamParser` turns raw bytes into channel messages. It implements running status (one status byte followed by repeated data pairs), messages split across chunks, SysEx skipping, and real-time bytes (clock/start/continue/stop) that may appear mid-message. A Note On with velocity 0 is a Note Off, and 0x8n is always a Note Off.
  - `MidiInput` owns `navigator.requestMIDIAccess({ sysex: false })`: permission grant/denial, input enumeration, `statechange` connect/disconnect, a 1–16 or All channel filter, CC64 sustain (a key released under the pedal keeps sounding until the pedal lifts) and CC120/CC123 panic. Disabling, disconnecting or switching device releases every held note.
- **`audio-engine.js`.** `startLiveVoice({ buffer, rate, velocity, offsetSec, trackId, pan })` plays a held, pitched voice with velocity → gain and returns `{ stop(releaseSec) }`; it is routed through the track insert chain (`trackNodes.get(trackId).input` — EQ, pan, gate, fader) or the master bus, never straight to `destination`. `panicLiveVoices()` silences everything. Live voices are tracked in `engine.liveVoices` and cleaned on `ended`.
- **Piano Roll bar** (`#pr-midi-bar`, between the title bar and the canvas): `#btn-midi-enable` (toggle, `aria-pressed`), `#midi-device-select`, `#midi-channel-select` (All + 1–16), `#btn-midi-record`, and `#midi-status` (`role="status"`, `data-kind="off|ok|warn|error|rec"`).
- **Feedback:** held notes paint their row and piano key green on the existing canvas; a red `REC` badge shows while recording. Live keys never mutate pattern data unless Rec is on.
- **Record (stretch goal, shipped):** captures Note On/Off into the active pattern on the 16-step grid, quantized to the current snap (snap finer than a 16th records at a 16th; Off records at a 16th), with one undo step per take. While the transport runs, notes land at the playhead; while stopped they land at time since Rec. Program Change (0xCn) selects the channel named in the Piano Roll header.
- **Honest degradation:** Firefox and Safari have **no Web MIDI API at all**. There, `requestMIDIAccess` is absent, the Enable button is disabled with one explanation line (Chromium/Edge only · use Play Notes, the piano keys, or Ctrl+T), and the pointer/typing paths keep working. Denied permission, "granted but no device", and device disconnect each have their own status line.

## 7. Feature B — MIDI file import / export — 2026-10-21

### What shipped

- **`app/public/midi-codec.js` (new, zero-dependency).** `parseSmf()` reads format 0 and 1 (format 2 is reported and read as format 1), 480-tick PPQ or the file's own division, tempo meta with the 20–260 BPM clamp, note on/off with velocity, program change, running status, SysEx skipping, real-time bytes, and truncated chunks (returns what it read + a warning — never throws). `buildSmf()` writes format 1: a conductor track with the project name, tempo and 4/4 signature, then one SMF track per Audius track at 480 ticks/beat. `smfToParts()` maps notes to the 16-step grid: one part per SMF track/channel that carries notes, one pattern per bar, notes quantized to the grid, `midi` preserved on every note.
- **Import UI.** `#btn-import-midi` + `#midi-import-input` (`.mid`/`.midi`, `audio/midi`, `audio/x-midi`) in the Library, and the existing drop zone now routes `.mid` files to the MIDI path and audio files to the audio path. Toasts are honest and specific: `Imported 3 tracks · 13 notes · 3 bar patterns`, plus follow-up lines for channels beyond the first 10, the 400-pattern import cap, off-grid quantization, folded pitches, and truncation.
- **Export UI.** `#btn-export-midi` in the Export dialog (beside the WAV render) writes `<project name>.mid`; the dialog reports notes/tracks/KB, refuses a note-free project with a reason, and states that audio clips are audio, not MIDI.
- **Mapping rules (as promised in the brief).** Each SMF track/channel containing notes → a new Audius track; each bar → a pattern named `<part> · Bar n`; empty/text/SysEx-only channels are ignored; more than 10 note-bearing channels → the first 10 import and the rest are counted in the toast. Tempo: the first tempo wins and is applied to the project when it differs.
- **Persistence.** Imported patterns store `trackId`, `barIndex` and per-note `midi`; `sanitizeProjectPayload` keeps them (validating `trackId` against the surviving tracks and clamping `midi`), so save → reload → open → export is note-identical. Malformed payloads still cannot throw.

## 8. DAW API — fully functional via an API (api-anything style) — 2026-10-20

Request: "Make the DAW fully functional via an API accordingly: https://github.com/DOGECOIN87/api-anything". Audius Studio now exposes the whole workstation as an API that follows api-anything's conventions. Full reference: `app/api/README.md`.

- **What was added** (all zero external dependencies):
  - `app/api/operations.json` — catalog of **56 operations** (9 server / 47 page) with api-anything ParamSchema fields (name, type, required, default, pattern, hint) plus readOnly/tier/timeoutMs.
  - `app/api/router.mjs`, `app/api/envelope.mjs`, `app/api/ws-hub.mjs` — every `/api/*` HTTP route (`sites`, `operations`, `sessions`, `call`, exports/imports storage, and the legacy `projects` endpoints kept behaviour-compatible for the UI). Every call answers api-anything's envelope `{ok,class,tier,data,ms}` / `{ok:false,class,reason,next}` with the classes `ok|drift|auth|rate|blocked|input|error`, and tier 1 (server) vs tier 3 (the page ran it). The hub is a hand-rolled RFC 6455 WebSocket server (masked frames, fragmentation, ping/pong, keepalive, per-call timeouts, session registry).
  - `app/public/api-bridge.js` + `buildApiBridgeHandlers()` in `app.js` — the live tab bridges over WS and executes tier-3 ops through the exact code paths the UI uses (undo snapshots, inspector clamps, engine sync): session/new/demo/save/load, transport (play/pause/stop/seek/tempo/loop/metronome), tracks & mixer, stem import from base64/url, every playlist edit (move/trim/split/slip/chop presets/transients/duplicate/reverse/mute/delete), per-segment inspector params, markers, meters, undo/redo, tool switch, and offline WAV export uploaded to the server and returned as download URLs. On static Cloudflare Pages hosting the probe fails and the bridge stays dormant.

## 9. Narrow-screen layout repair (phone header, tabs, snap, tempo) — 2026-10-21

The user's screenshot ("This is not correctly designed yet") showed the compact layout leaking at phone widths: controls hanging past the right edge, a truncated snap label, and a squashed Library/Playlist tab pair. Measured in Chromium 153 at 320/341/360/375/390/414/430/431/683/760/761/1024/1360/1361/1920, then fixed in `styles.css` (+ one markup-free label change in `index.html`).

### What was wrong (measured, not guessed)

1. **Closed `<details>` popovers still laid out.** `.transport-readouts-content` and `.transport-extras-content` were absolutely positioned inside a closed `<details>`, and Chrome still gave them a box. At 341px the read-outs panel started at x=309 and ended at x=353 (12px past the screen), pushing `body.scrollWidth` to 353. At 430px it started at 452.
2. **A 421–430px dead zone.** The phone tempo rules stopped at `max-width: 420px` while the phone layout ran to 430px, so in that band the `.000` wheel and both ± steppers reappeared: the tempo box grew from 58px to 187px and the transport's own scrollWidth hit 488px at 430.
